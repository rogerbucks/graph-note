# Where things live — the Python library

A host puts `src/` on `sys.path` and imports the four entry points by name. Each re-exports every name it has always had, from where it lives now; the code is in `src/graphspec/`, one feature to a module.

## The entry points, in `src/`

- `gql_profile.py` — reads data blocks in the document profile (§3) into a plain graph, with no database; and a graph's style blocks into its nudges (`read_style`, editor spec §6), as the plugin's core reads them.
- `graph_rules.py` — the spec's rules on that plain graph.
- `graph_spec.py` — the conformance suite's entry point: it reads, checks, runs processes, serves views and fills hashes from the reader's reading by default, and through Grafeo when a host sets `PARSER = 'grafeo'` (database work only); a setting a host assigns here is forwarded to `src/graphspec/engine/settings.py`.
- `graph_svg.py` — lays a graph out with Graphviz as themed SVG; its style is `graph_svg.style.json` beside it. `dot_source` and `render` take the keys of boxes drawn under a suggested name (`suggested`, from the warnings `read_for_drawing` lists), dashed and labelled as the core draws them. `nudged_source` writes a graph's nudges into the source, and `directions` gives the directions laid out, only the one a direction nudge sets, as the core's `style-source.ts` and `render.ts` do; `render` takes the `nudges` and `direction` that `read_style` gives (python_honours_nudges). `arrowless_source` and `inline_source` (from `graphspec/style/`) write the arrowheads a style hides and the properties it shows into the source, before the nudges, and `render` takes them as `arrowless` and `inline` (arrows_both_renderers); `flow_source` writes the links a Flow moves, first after the diagram type, and `render` takes them as `flow` (links_show_flow). `typed_source` (from `graphspec/style/diagram_types`) lays the source out as the diagram type chosen, before all of those, and `render` takes its plan as `diagram`; `directions` lives there too, re-exported here (type_both_renderers). `nudged_source` lives in `graphspec/style/nudges`, re-exported here. `folded_source` and `routed_source` (from `graphspec/style/fold_source`) write what a View menu folds and merges and how links are routed (editor spec §25) last, and `render` takes them as `folding` and `routing`; `drawn_source` is the whole source `render` lays out in one direction, every step in the core's order. `picture_source` (from `graphspec/style/picture`) keeps room at the top of each box a Picture draws an image on, a square marked for a host to fill, after the properties shown and before the nudges and folds, and `render` takes those boxes as `pictures` (animated_image_shown; graph_svg loads no image).

## The code, in `src/graphspec/` (packages: each folder's `__init__.py` says what it holds)

- `src/graphspec/reader/` — gql_profile's: whitespace as GQL names it, never `isspace()` or `splitlines()` (`whitespace`), tokens and header (`lexer`), `grammar`, the `store`, `to_gql`, drawing in part (`drawing`, which, as the core's `blocks.ts`, never reads a block drawn `· FROM` a file or a note as data), a block's items (`block_items`), `canonical_hash`, `syntax_check`, the `///` notes and `//@` lines each element owns (`owned_comments`, §26 and §27, held with the JavaScript reader to `packages/graph-spec/test/owned-comment-cases.json`), each note's text and summary and the lines a note above belongs to none of (`notes`, editor spec §24, held to the same table, and to the JavaScript reader run live by `tests/test_notes.py`); and, as the plugin's core does, the things written in a block (`written_things`), a name suggested from a text (`name_suggestions`) and the names suggested for things written without one, which drawing reads them under (`name_gaps`). `tests/name_cases.json` holds them and the core to one table.
- `src/graphspec/style/` — gql_profile's `read_style` (editor spec §2, §6, §14, §15, §18), the core's `style.ts` step for step as far as what graph_svg draws goes: a graph's style blocks (`style_of`, in `reader/drawing`, which never reads one as data) read with `read_for_drawing`, each thing's kind and keys, and each nudge, Show, Arrows, Diagram, Flow, Links and Picture, checked against the graph (`checks`), those against each other (`conflicts`), the fixes' nearest names, counted in UTF-16 units as JavaScript counts (`near_names`), and the words and keys (`words`); the arrowheads a drawing hides (`arrows`, the core's `arrows.ts`), the links it moves and how, each moving link's label opened by its icon and marked with the classes a style sheet moves it by (`flow`, the core's `link-flow.ts`; the SVG graph_svg writes is still, as the plugin draws under reduced motion), and the properties it shows inline, each value said as JavaScript says it, a long one cut short (`inline`, the core's `inline-properties.ts`); the boxes a Picture draws an image on and the room kept for it (`picture`, the core's `picture.ts`); which diagram types fit a graph and why not, the one drawn (the chosen one while it fits, else a network, with the nearest that fits), and each laid out (`diagram_types`, the core's `types.ts` and graph-layout.js `typedSource`; the table is the plugin's to draw, so here it is drawn as a network, and `render_args` says so on stderr); the nudges written into the source (`nudges`); folding (`folding`, the core's `untangle-fold.ts` and the switches of `view-switches.ts`: `BUSY_HUB`, `fold_plan`, `drawn_groups`, `links_of`, and `starting_switches`, as the plugin's default settings start a graph, the style graph's Links merges its links, and a view was saved as shown) and the plan written into the source (`fold_source`: a hub's stub, a group's box, trunks between groups, and the links routed); and a graph ready to draw (`drawn`): `graph_parts`, its boxes and written links as the core chooses them, each link in its schema's words (its own or a shared one's), with their properties, and `render_args`, what `graph_svg.render` draws a graph with as the plugin draws it in a view or the whole graph, style and routing and all, folded only when switches are given (as an export and the Claude Code pane, it folds nothing by default), but never the links the plugin guesses from a near miss (graph_svg re-exports it). Look and ViewStyle are drawn by the plugin alone, so only their keys are checked here; of a Shown, its view and the switches it was saved with are checked too, as graph_svg draws them.
- `src/graphspec/rules/` — graph_rules's: `plain_graph`, `canonical_json`, §5 `schema_types`, §18 `projection`, §20 `likelihood`, `certainty` and `certainty_checks`, §22 `paths`, §15 `lens`, §23 `judgements` and `judgement_checks`, §24 `servings` and `changesets`, §25 `completeness`, `graph_check` (every rule on one graph), `views`, `guessed_readings`.
- `src/graphspec/engine/` — graph_spec's: host `settings`, `optional_imports` (Grafeo, PyYAML, lxml, rfc8785, loaded on first use), Grafeo `queries`, §18 `projection`, §5 `schema`, §22 `paths`, §24 H1 `dialect_lint` and `embedded_queries`, §24 H4 `changesets`.
- `src/graphspec/engine/documents/` — a document's GQL block read (`reading`), the hash filler (`fill`), the classification note (`classification`).
- `src/graphspec/engine/joining/` — §21: `config`, `restating`, `breaches`, `claims`, `union`, `merge3`, `finish` (and join, join3), `audit` (held, lost, invented), `emit`, `named_rules`, `gql_rules`.
- `src/graphspec/engine/process/` — §7, §16: the process engine (`machine`) and its SCXML export (`scxml`). Given the block the process is written in, `to_scxml` keeps each `///` note on a State or a transition as an XML comment directly before its element (editor spec §24, note_standard), a transition's found by the order the block writes it in, never the order a source gives its rows in, written by `note_comment` as the core's `xml-comment.ts` writes one and read back by `comment_note`; `tests/note_comment_cases.json` holds both languages to one table, and `tests/test_scxml.py` reads the export back.
- `src/graphspec/engine/certainty/` — §20: the likelihood `scale`, cached values (`caches`), `track_record`, `checks`.
- `src/graphspec/engine/judgements/` — §23: `basis` and its hashes, `review`, `checks`.
- `src/graphspec/engine/serving/` — §24 H3: the `view_server` and its `checks`.

## Tests, in `tests/`

`test_reader_agrees_with_grafeo.py` holds the reader and its plain rules to Grafeo's answers (req:17.engine-agreement), on the shared cases and on generic cases in `tests/agreement/` (one JSON file per area, each block a list of lines; `classification.md` there is a generic destination matrix). Grafeo is the reference only: a test dependency, never one the readers need.

Grafeo is not installed by a plain install (req:14.no-engine-install): it is the `grafeo` extra, for database work, and the `reference` dependency group of a working copy. A test that needs it uses `engine_support.needs_engine` (or `module_needs_engine` in `setUpModule`): skipped without Grafeo, as CI's `python-no-engine` job runs (`uv sync --locked --no-default-groups`), but run and failed in CI's `python` job, which sets `GRAPH_SPEC_ENGINE=required`.

`test_view_parity.py` holds Grafeo to `tests/view_cases.json`, the table of views the core's `view-parity.test.js` holds the core to: each view's query, run in Grafeo as written, returns the things the core returns (views_agree_with_grafeo), and, of a fixed list of GQL's and Cypher's words kept in the test (never the lists it tests), Grafeo refuses as a name and as a kind exactly the words the core keeps from them.

`test_graph_svg_nudges.py` holds graph_svg and `read_style` to the core, run live by Node, on `tests/nudge_cases.json`: for each note, the same problems reading its data and its styles, and the same source in each direction laid out, nudges written in, byte for byte (python_honours_nudges). The core's `layout-parity.test.js` holds the same from the JavaScript side.

`test_graph_svg_types.py` does the same on `tests/type_cases.json` for the diagram types: the same answer for whether each type fits and why not, the same type drawn, and the same source in each direction (type_both_renderers).

`test_graph_svg_folds.py` does the same on `tests/fold_cases.json` for a busy hub folded into a stub, a group into a box, links between groups merged into a trunk and links routed, as a card's View menu state started from the plugin's default settings folds them when a case turns its switches, and with nothing folded when it does not: the same problems reading each Links, and the same source (untangle_hubs, untangle_groups, untangle_merge, untangle_routing). Its `python_answer` is the Python side `layout-parity.test.js` runs.

`test_graph_svg_flow.py` does the same on `tests/flow_cases.json` for links a Flow moves: the same problems, links moving and source, through `render(**render_args(…))` (links_show_flow); the core's `link-flow-parity.test.js` runs its `python_answer`.

`test_graph_svg_picture.py` does the same on `tests/picture_cases.json` for pictures on boxes: the same problems, boxes with a picture and source (animated_image_shown); the core's `picture-parity.test.js` runs its `python_answer`.

`test_graph_svg_styled.py` does the same on `tests/style_cases.json` for arrowheads hidden and properties shown inline, each note drawn in the view it names: the same problems, links without arrowheads, rows and source (arrows_both_renderers). Its `python_answer` is the Python side `layout-parity.test.js` runs.

Otherwise named after the module they test. `test_<entry point>_entry_point.py` hold each entry point to every name it had (`entry_points.json`) and to importing with only `src/` on the path.
